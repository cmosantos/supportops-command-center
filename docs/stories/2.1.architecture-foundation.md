# Story 2.1 — Architecture Foundation

## Status

Ready for Review — implementation remains blocked pending human Phase 2 approval.

## Context

SupportOps Command Center is a local-first incident-assistance application for N1
and N2 support. This story records the architecture needed for later incremental
implementation. It does not deliver product functionality.

## Objective

Define the isolated project boundary, architecture, domain models, SQLite schema,
ports, ADRs, test traceability, delivery gates, and unresolved decisions without
modifying the AIOX core or implementing application behavior.

## In scope

- Project-local Git repository and safe ignore rules.
- CLI-first modular architecture and dependency rules.
- Conceptual domain, persistence, provider, export, and approval contracts.
- Versioned configurable priority policy design.
- Logical deletion and append-only lifecycle/approval audit design.
- Local lexical knowledge-search design.
- Optional Ollama provider and fake/mock testing contract.
- ADRs, traceability, incremental plan, progress, and pending decisions.

## Out of scope

- Python package or executable CLI.
- SQLite database, schema migrations, or repositories.
- Streamlit screens or dashboard.
- Runbook content and knowledge-search implementation.
- Classification, hypotheses, troubleshooting, exports, Docker, or Ollama code.
- Any shell-command execution capability.
- Changes outside `projects/supportops-command-center/`.

## Acceptance criteria

1. All Phase 2 artifacts reside under the isolated project directory.
2. A local Git repository is initialized without initializing Git at the AIOX root.
3. Architecture documents define presentation, application, domain, ports, and
   infrastructure with inward dependency direction.
4. The CLI is canonical and must pass its essential E2E gate before Streamlit.
5. Domain models cover intake, triage, evidence, hypotheses, plans, suggestions,
   approvals, documentation, status history, deletion, and metrics.
6. SQLite design covers automatic future bootstrap, versioned migrations,
   constraints, transactions, indexes, append-only history, and soft deletion.
7. Priority is a single versioned configuration; invalid configuration fails
   safely; complete boundary cases remain assigned to the Support Specialist.
8. Mean handling time is defined as latest close minus creation for currently
   closed, non-deleted incidents; SLA waiting periods are not deducted in V1.
9. Approval is persisted against the exact action ID/version/digest and never
   triggers execution.
10. The architecture contains no shell executor or arbitrary-command interface.
11. Knowledge search is local, lexical, explainable, and behind a replaceable port.
12. Ollama is disabled by default, model-configurable, and covered by fake/mock
   contract cases without becoming a mandatory dependency.
13. ADRs record the approved decisions and consequences.
14. Every requirement maps to a canonical future story and one or more test IDs.
15. Progress, pending decisions, risk register, and actual File List are current.

## Security requirements

- No password/token fields or real credentials.
- No shell executor, `shell=True`, arbitrary command endpoint, or automatic action.
- Bound SQL parameters and application-owned filesystem roots in implementation.
- Redacted structured logs and safe presentation errors.
- LLM output treated as untrusted structured input.
- Human approval is immutable traceability, not execution authority.
